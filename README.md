# sourcecraft-mcp

MCP-сервер и CLI для [SourceCraft](https://sourcecraft.dev) REST API.

> Проект в разработке. Установка, подключение к MCP-клиентам и описание инструментов появятся в первом релизе.

## Что умеет

- Все операции SourceCraft API доступны как MCP-инструменты. Они генерируются из официальной спецификации при сборке.
- Поиск по всем операциям API через `api_search`, включая отключённые на сервере: инструмент подскажет флаг, который их включает, и покажет схему аргументов операции.
- Произвольные запросы к API через `api_request` — для операций без отдельного инструмента. Путь только относительный (`/repos/...`), заголовки задать нельзя. Уровень доступа определяется по совпадающей операции API, а если её нет — по методу (GET — чтение, POST/PUT/PATCH — запись, DELETE — удаление). Наборы инструментов `api_request` не ограничивают. Запись секретов через `api_request` запрещена: API ждёт значение в base64.
- Токен хранится в системном хранилище (macOS Keychain и аналоги), у каждого MCP-клиента свой профиль.
- По умолчанию только чтение. Запись и удаление включаются явно.
- Значения секретов не попадают в ответы MCP без явного запроса.
- Секреты репозитория можно использовать в командах оболочки (`sourcecraft-mcp secret exec`), не показывая значения агенту.

## Запуск сервера

MCP-клиент запускает сервер командой `sourcecraft-mcp serve` (stdio). Токен берётся из системного хранилища по профилю: `--profile` (по умолчанию `default`), сохранить токен — `sourcecraft-mcp auth login --profile <профиль>` или `sourcecraft-mcp connect <клиент>`.

| Флаг | Назначение |
| --- | --- |
| `--allow-write` | Регистрировать инструменты, которые создают и меняют данные. |
| `--allow-destructive` | Регистрировать инструменты удаления (включает `--allow-write`). Также нужен, чтобы сделать репозиторий публичным. |
| `--toolsets a,b` | Только указанные наборы инструментов; список — `sourcecraft-mcp toolsets`. |
| `--allow-secret-values` | Разрешить показывать значения секретов по явному запросу инструмента (`reveal_values: true`). |
| `--allow-path <каталог>` | Дополнительный каталог для локальных файлов; можно повторять. |
| `--base-url <URL>` | Адрес API; по умолчанию `SOURCECRAFT_BASE_URL` или `https://api.sourcecraft.tech`. |
| `--timeout <секунды>` | Таймаут запроса к API, по умолчанию 60. |
| `--max-response-bytes <байты>` | Размер ответа, который получает агент, по умолчанию 256 KiB; больший ответ обрезается. |

Если флаги доступа, `--allow-secret-values` или `--toolsets` не заданы, используются настройки профиля, сохранённые `connect`.

### Секреты

- Значения секретов репозитория (`list_secrets` и все ответы эндпоинтов `/repos/…/secrets`, включая ошибки) заменяются на `"[redacted]"`; ключи и метаданные видны. В ответ добавляется пояснение, что значения скрыты.
- То же действует для `api_request`. Для эндпоинтов секретов `api_request` не принимает `save_to` и `body_file`: файл обошёл бы вырезание значений.
- Во всех ответах скрываются строковые значения полей, похожих на учётные данные: `password`, `passwd`, `passphrase`, `secret`, `token`, `access_token`, `refresh_token`, `private_key`, `api_key`, `client_secret`, `webhook_secret` и имена с такими окончаниями (`db_password`). Токены пагинации (`next_page_token`) и флаги (`has_password`) не скрываются.
- Показать значения секретов можно только на сервере с `--allow-secret-values` и только по явному запросу: `list_secrets` с `reveal_values: true`. Без флага такой вызов отклоняется. Поля учётных данных скрываются и при раскрытии.
- Секрет записывается инструментом `secret_set` (нужен `--allow-destructive`): он принимает открытый текст в `value` или путь к локальному файлу в `value_file` и сам кодирует значение в base64. С `value_file` значение не попадает в контекст агента. `trim_trailing_newline` убирает один завершающий перевод строки; по умолчанию включён для `value_file` и выключен для `value`. Пустое значение отклоняется.

## Секреты в командах оболочки

Секреты часто нужны в командах: развернуть сборку на сервер, передать ключ в `scp` или `ssh`, запустить скрипт деплоя. Команды `sourcecraft-mcp secret` позволяют агенту (и человеку) использовать секрет, не видя его значения. Токен берётся из системного хранилища по профилю, как у `serve`.

Общие флаги: `--profile` (по умолчанию переменная окружения `SOURCECRAFT_MCP_PROFILE`, иначе `default`; переменная задаёт только имя профиля, не токен), `--repo <org>/<repo>` или `--repo-id <ID>`, `--group` (группа секретов), `--base-url`.

| Команда | Что делает |
| --- | --- |
| `secret exec --repo <org>/<repo> --env NAME=KEY -- <команда> [аргументы…]` | Запускает команду с секретом `KEY` в переменной окружения `NAME`. `--env` можно повторять; `--env KEY` — переменная с именем ключа; `--all` — все секреты под своими ключами; `--prefix P` добавляет префикс к именам из ключей. stdin наследуется, код завершения команды возвращается. |
| `secret write --repo <org>/<repo> KEY --to <путь> [--mode 600] [--force]` | Записывает значение в новый файл с правами 0600 и печатает только путь и размер. Существующий файл или ссылка не перезаписываются без `--force`. |
| `secret list --repo <org>/<repo>` | Печатает ключи, без значений. |
| `secret get --repo <org>/<repo> KEY --reveal` | Печатает значение. Без `--reveal` завершается ошибкой и подсказывает `exec` и `write`. Если stdout не терминал, в stderr напоминает, что значение попало в вывод вызывающей программы. |

`secret exec` запускает команду напрямую, без оболочки. В выводе команды (stdout и stderr) значения переданных секретов и их base64 заменяются на `***`, в том числе если значение разрезано между порциями вывода. Значения короче 4 байт не маскируются (иначе испортился бы вывод) — об этом, как и о пустом значении, предупреждение в stderr с именем ключа. Ключ, которого нет в репозитории, — ошибка до запуска команды.

Чтобы подставить переменную в командную строку, запустите оболочку сами и возьмите скрипт в одинарные кавычки: тогда `$NAME` раскроет дочерняя оболочка, а не ваша.

```bash
# Скопировать секрет на сервер без локального файла.
sourcecraft-mcp secret exec --repo acme/web --env CONF=APP_CONFIG -- \
  sh -c 'printf %s "$CONF" | ssh deploy@host "cat > /etc/app/config"'

# Программе нужен файл (ssh -i): записать, использовать, удалить.
sourcecraft-mcp secret write --repo acme/web DEPLOY_KEY --to /tmp/deploy_key && \
  scp -i /tmp/deploy_key build.tar deploy@host: ; rm -f /tmp/deploy_key
```

Правила для агентов (сервер передаёт их в инструкциях MCP с точным профилем и путём к бинарнику):

- использовать `secret exec` и `secret write`, а не читать значение;
- не выводить переменные с секретами (`echo`, `printf` в терминал, логи), не записывать их в файлы, которые потом читаются, и не преобразовывать (кодировать, разбивать) в выводе;
- `secret get --reveal` — только когда пользователь явно просит показать значение.

Маскирование защищает от случайной утечки, но не является границей безопасности: значение, которое команда преобразовала (hex, URL-кодирование, по символу в строке, base64 со сдвигом внутри более длинных данных), не распознаётся. По той же причине `secret get --reveal` не требует настройки `--allow-secret-values`: она ограничивает ответы MCP-сервера, а агент с доступом к оболочке и к `secret exec` может получить значение и без `get`. Решение о доступе агента к оболочке и профилю принимает пользователь.

Инструменты, которые загружают файлы, принимают путь к локальному файлу. Путь должен лежать в рабочем каталоге сервера (кроме корня файловой системы и домашнего каталога), во временном каталоге системы или в каталоге из `--allow-path`; выход через `..` и символические ссылки отклоняется.
